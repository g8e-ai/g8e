# FIPS 140-3 Compliance

Last Updated: 2026-08-16
Version: v1.7.6

## Overview

g8e uses the Go Cryptographic Module v1.0.0 (CMVP Certificate #5247, CAVP A6650) in FIPS 140-3 approved mode. This document is the single source of truth for g8e's FIPS compliance claim. Other documentation cross-references this page rather than duplicating details.

## Validated Module

- **Module**: Go Cryptographic Module v1.0.0
- **CMVP Certificate**: #5247
- **CAVP Certificate**: A6650
- **Standard**: FIPS 140-3
- **Module Type**: Multi-Chip Standalone (software)
- **Security Level**: Level 1

## Validated Algorithms

The following algorithms are within the validated boundary when FIPS mode is active:

- **EdDSA (Ed25519)**: KeyGen, KeyVer, SigGen, SigVer per FIPS 186-5 (CAVP A6650). Used for L2 consensus signatures, L5 actuator receipts, L3 notary proofs, and trusted signer verification.
- **ECDSA**: P-224, P-256, P-384, P-521 per FIPS 186-5. P-256 is enforced for all PKI certificate signatures. WebAuthn passkey assertions use the platform default credential parameter set, which includes ECDSA P-256 as the preferred algorithm.
- **SHA-2**: SHA-224/256/384/512, SHA-512/224, SHA-512/256. SHA-256 is used for transaction hashes and key fingerprinting.
- **SHA-3**: SHA3-224/256/384/512.
- **AES**: AES-128/192/256 in GCM, CBC, CTR, Key Wrap, and ECB modes. AES-256-GCM is used for vault encryption and keystore secret encryption. AES Key Wrap (RFC 3394) is used for DEK wrapping.
- **HMAC**: HMAC-SHA2, HMAC-SHA3. An auditor HMAC key is provisioned and stored in the keystore for auditor authentication.
- **HKDF**: HKDF-SHA256, validated under four NIST designations (SP 800-108 Feedback KDF, SP 800-56C two-step, IG D.P OneStepNoCounter, SP 800-133 Section 6.3). Used for vault Key Encryption Key derivation.
- **TLS 1.3 key schedule**: Validated per IG 10.4.B Resolution 7.
- **ML-KEM (FIPS 203)**: Post-quantum key encapsulation mechanism, including the `X25519MLKEM768` hybrid for TLS key agreement.

## Excluded Algorithms

The following algorithms are **not** within the validated boundary and are excluded from g8e's FIPS compliance claim:

- **X25519 key agreement**: Not SP 800-56A rev3 compliant. Excluded from Go's FIPS TLS mode. g8e removes X25519 from all TLS `CurvePreferences` lists and replaces it with `X25519MLKEM768` (FIPS 203 validated hybrid), P-384, and P-256.
- **Ed25519 in TLS certificate signatures**: Go's FIPS TLS signature algorithms omit Ed25519. Ed25519 is validated for application-layer signatures (consensus, receipts, notary) but **not** for TLS certificate signatures. g8e enforces ECDSA P-256 for all PKI-issued certificates and rejects Ed25519-signed certificates at load time with a fail-closed guard.

## Operating Environment

CMVP Cert #5247 is validated for specific operating environments. g8e's FIPS compliance claim is restricted to the following vendor-affirmed OE:

- **OS**: Debian GNU/Linux 12 (Bookworm)
- **Architecture**: linux/amd64
- **Runtime image**: Debian GNU/Linux 12 pinned by digest in `Dockerfile`
- **Vendor-affirmed**: Debian GNU/Linux 12 is listed in Table 3 (Vendor-Affirmed OEs) of the certificate security policy.

The FIPS compliance claim does not extend to other operating systems or architectures. The `Dockerfile` hardcodes `GOOS=linux GOARCH=amd64`, so the restriction is satisfied.

## Build-Time Activation

FIPS mode is activated natively at build time via the `GOFIPS140` environment variable. No runtime environment variable is required.

- **Build variable**: `GOFIPS140=v1.0.0` (pinned to the certified, frozen module version)
- **Makefile target**: `make build-fips` produces `bin/g8e-fips-linux-amd64` (local non-Docker testing)
- **Docker**: `Dockerfile` sets `ENV GOFIPS140=v1.0.0` in the builder stage only. The runtime stage does not set the variable; the binary enters approved mode automatically on startup.
- **CGO**: `CGO_ENABLED=0` (the Go FIPS module is pure Go; CGO is not required)
- **Build-time self-check**: `Dockerfile` runs `g8e version --fips` during the build to confirm FIPS mode is active (exits 0 with a warning when enforcement is off, the expected posture).

The `GOFIPS140` setting is build-time only. It selects the module version linked into the binary and enables FIPS mode by default (the `fips140` GODEBUG defaults to `on`). The running binary does not read `GOFIPS140` at runtime.

## Runtime Verification

Operators and auditors verify FIPS mode status via the `g8e version --fips` subcommand, which queries the linked Go Cryptographic Module directly:

- **Approved mode**: Reports whether the binary is running in FIPS 140-3 approved mode.
- **Enforcement**: Reports whether FIPS mode is enforced (non-compliant algorithms panic).
- **Module version**: Reports the linked module version (e.g., `v1.0.0`).

The command exits non-zero only if approved mode is not active. If approved mode is active but enforcement is off, the command prints a warning and exits 0.

The `make verify-fips` target builds the FIPS variant and runs this self-check under enforcement mode (`GODEBUG=fips140=only`), exiting non-zero if FIPS mode is not active or enforcement is not engaged.

Go runs integrity self-checks at startup and known-answer/pairwise-consistency tests at startup or first use of each algorithm. The binary aborts if any self-test fails.

## CI Pipeline

The FIPS CI workflow builds with `GOFIPS140=v1.0.0`, runs `make verify-fips`, executes the test suite with the FIPS module linked, and verifies static linking.

## Docker Usage

The repo-root `Dockerfile` is the single Docker build path. It always builds with FIPS 140-3 approved mode enabled; there is no separate FIPS variant.

Build the image:

```bash
docker build -t g8e .
```

The resulting image runs in FIPS 140-3 approved mode by default. No runtime environment variable is needed. Enforcement is off by default; set `GODEBUG=fips140=only` in the container environment to reject non-approved primitives at runtime.

Demo and production compose files both build from this Dockerfile. Demos use `context: ../..` (from `demos/<org>/`) to reach the repo root; the root `docker-compose.yml` uses `context: .`.
