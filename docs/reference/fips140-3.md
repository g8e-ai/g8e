# FIPS 140-3 Compliance

Last Updated: 2026-09-08
Version: v2.1.7

## Scope of the Claim

g8e Linux AMD64 artifacts produced by the release and container build paths link Go Cryptographic Module v1.0.0 and enter FIPS 140-3 approved mode by default. The module is validated under CMVP Certificate #5247 and CAVP Certificate A6650. This claim covers use of approved services from that module in the operating environment described below; it is not a separate CMVP validation of the g8e application or a claim that every cryptographic operation available through g8e is approved.

A deployment remains within this claim only when all of the following are true:

- The deployed binary is the Linux AMD64 artifact built with `GOFIPS140=v1.0.0`.
- The binary runs on the Debian GNU/Linux 12 operating environment described below.
- `g8e version --fips` reports approved mode enabled and module version `v1.0.0`.
- The deployment uses approved algorithms, key sizes, and externally supplied key material appropriate to its security policy.

The claim does not cover other operating systems or architectures, binaries produced by an ordinary `make build` or `go install`, a process started with `GODEBUG=fips140=off`, or use of non-approved cryptographic services. Linking a validated module does not by itself establish compliance with every regulatory requirement that applies to a deployment.

## Validated Module

- **Module**: Go Cryptographic Module v1.0.0
- **CMVP validation**: [Certificate #5247](https://csrc.nist.gov/projects/cryptographic-module-validation-program/certificate/5247), active through April 26, 2031
- **Algorithm validation**: CAVP Certificate A6650
- **Standard and level**: FIPS 140-3, Security Level 1
- **Module type**: Multi-Chip Standalone software module

Certificate #5247 states that the module provides no assurance about the minimum strength of generated security-sensitive parameters, externally loaded keys or bit strings, or parameters established from externally loaded material. Operators remain responsible for key strength, key provenance, and approved use of the module. The [Go FIPS 140-3 documentation](https://go.dev/doc/security/fips140) describes module selection, approved mode, self-tests, and runtime controls.

## Cryptography Used by g8e

g8e uses Go standard-library cryptography for its primary security paths. When the selected binary runs in approved mode, these calls route through the linked module where the Go module exposes the corresponding approved service.

- **TLS and mTLS**: g8e requires TLS 1.3 and configures `X25519MLKEM768`, P-384, and P-256 as its key-agreement preferences. Standalone X25519 is absent from g8e curve preferences. Go's TLS implementation also suppresses protocol versions, cipher suites, signature algorithms, and key exchanges that it does not permit in FIPS mode. The ML-KEM service is validated under FIPS 203; this does not make standalone X25519 an approved service.
- **Platform PKI**: g8e generates root, intermediate, service, and enrolled leaf keys on ECDSA P-256. Certificate and revocation-list signatures use ECDSA with SHA-256. Certificate signing requests with non-P-256 public keys are rejected, and persisted CA certificates with Ed25519 signatures are rejected when the platform PKI loads them.
- **Application signatures**: Ed25519 signs and verifies consensus decisions, notary proofs, actuator receipts, enrollment messages, audit and compliance evidence, and other application-layer records. EdDSA key generation, key verification, signature generation, and signature verification are approved services in Certificate #5247. This approval does not extend Ed25519 to TLS certificate signatures, which Go TLS does not permit in FIPS mode.
- **Data protection**: Vault records and keystore secrets use AES-256-GCM. Vault key-encryption keys use HKDF-SHA-256, and hashes and fingerprints use SHA-256. The vault wraps data-encryption keys with a g8e implementation of RFC 3394 built from the module's AES block primitive; g8e does not claim that composite key-wrap implementation as a separately validated service under Certificate #5247.
- **Random generation**: Key, nonce, and token generation uses `crypto/rand`. In FIPS mode, Go implements it with an SP 800-90A deterministic random bit generator and mixes in the platform CSPRNG as additional input.
- **WebAuthn**: Registration advertises the WebAuthn library's default algorithm set, with ES256 first, followed by other ECDSA, RSA, RSA-PSS, and EdDSA choices. The authenticator selects the credential algorithm, so deployments include the selected authenticator algorithm and key strength in their compliance assessment.
- **SSH**: Native SSH operations use `golang.org/x/crypto/ssh`. When FIPS mode is active, that package filters its default key exchanges, ciphers, message authentication codes, host-key algorithms, and public-key authentication algorithms. SSH interoperability and any explicitly supplied SSH configuration remain deployment-specific and are not covered by the TLS configuration claim above.

The CMVP certificate is authoritative for the complete list of approved services. g8e does not claim algorithms merely because a dependency implements them or because they are available when strict diagnostic enforcement is disabled.

## Operating Environment

The g8e claim is restricted to this operating environment:

- **Operating system**: Debian GNU/Linux 12 (Bookworm), listed as a vendor-affirmed operating environment in the Certificate #5247 security policy
- **Architecture**: Linux AMD64
- **Runtime image**: The repository-root `Dockerfile` uses a digest-pinned Debian GNU/Linux 12 runtime image and installs the Linux AMD64 artifact as the container entry point
- **Linkage**: `CGO_ENABLED=0` produces a statically linked binary

The container builder also produces Linux ARM64 and Linux 386 artifacts with the module linked, but the g8e compliance claim does not include those artifacts. Windows and Darwin artifacts are built without `GOFIPS140`.

## Build Paths

`GOFIPS140` is a build-time Go toolchain setting. Selecting `v1.0.0` links the frozen validated module and changes the executable's default `fips140` runtime setting to `on`.

- `make build-fips` builds `bin/g8e-fips-linux-amd64`, writes its SHA-256 checksum, and copies the binary to `g8e-fips` for local verification.
- `make build-all` sets `GOFIPS140=v1.0.0` for each Linux target and explicitly unsets it for Windows and Darwin targets. The release workflow uses this target.
- The repository-root `Dockerfile` runs `make build-all`, checks the Linux AMD64 artifact with `g8e version --fips`, and copies that artifact into the runtime image.
- Ordinary `make build` and `go install` invocations do not select the validated module automatically. Set `GOFIPS140=v1.0.0` during compilation or use one of the build paths above.

The running process does not read `GOFIPS140`. Its approved-mode default is embedded at build time, but the startup setting `GODEBUG=fips140=off` overrides that default and disables approved mode.

## Runtime Verification

Run `g8e version --fips` inside the deployed environment. The command queries `crypto/fips140` and reports the approved-mode state, diagnostic enforcement state, and linked module version. It exits nonzero when approved mode is disabled; when approved mode is enabled and enforcement is disabled, it prints a warning and exits zero.

For the default container, run `docker run --rm g8e version --fips`. Confirm that the output reports `FIPS 140-3 mode: enabled`, `FIPS enforcement: disabled`, and `FIPS module version: v1.0.0`. The repository Compose files do not set `GODEBUG`, so they use this default state.

Go performs a module integrity check at startup, known-answer tests at startup or first use, and pairwise consistency tests for generated keys. A failed mandatory self-test prevents the cryptographic service from continuing.

### Diagnostic Enforcement

`GODEBUG=fips140=only` enables Go's best-effort diagnostic enforcement. Non-approved operations return errors or panic where Go can detect them. Go documents this mode as an assessment and debugging aid that can produce false positives or false negatives, can introduce crashes, is not required by the module security policy, and is not intended as a production control.

`make verify-fips` builds the Linux AMD64 FIPS artifact and runs only its `version --fips` status check with `GODEBUG=fips140=only`. Passing this target confirms that the binary links module v1.0.0 and can start with approved mode and diagnostic enforcement enabled. It does not demonstrate that every g8e feature has executed under diagnostic enforcement.

## CI Verification

The FIPS CI workflow performs the following checks on an Ubuntu Linux AMD64 runner:

1. `make verify-fips` builds the dedicated artifact and checks its module state with diagnostic enforcement enabled.
2. Unit and integration tests compile with `GOFIPS140=v1.0.0` and run in approved mode. They do not set `GODEBUG=fips140=only`.
3. The workflow verifies that `bin/g8e-fips-linux-amd64` is statically linked and has no dynamic library dependencies.

These checks verify build configuration and regression behavior. They do not replace deployment verification in the claimed Debian GNU/Linux 12 operating environment.

## Build and Verify the Container

1. Build the image with `docker build -t g8e .`.
2. Inspect the running artifact with `docker run --rm g8e version --fips`.
3. Confirm approved mode is enabled, the module version is `v1.0.0`, and the reported platform is `linux_amd64`.
4. Record the image digest and command output as deployment evidence.

Demo and root Compose configurations build the same repository-root `Dockerfile`. Verify the deployed container rather than inferring module status from the image source or tag.
