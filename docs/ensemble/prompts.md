# Prompts

## Overview

g8ee implements a modular, layered prompt architecture that generates system prompts, persona identities, tool descriptions, and verification templates. The architecture eliminates inline triple-quoted prompt strings by storing all prompt components as discrete text files under `app/prompts_data/`, managed by an LRU-cached loader. Prompt composition enforces strict separation of concerns between shared platform governance, agent personas, execution modes, and dynamic runtime context, while optimizing section ordering for prefix-cache reuse in local and hosted LLM inference backends.

## Modular System Prompt Assembly

The system prompt for reasoning and responder agents (`sage`, `dash`) is constructed dynamically by `build_modular_system_prompt` (`app.llm.prompts`). The builder concatenates sections in a strict order designed to maximize prefix-cache hits in engines like `llama.cpp` and `vLLM`. The static, shared governance prefix appears first so that multiple agents and turns reuse cached prompt tokens. Per-agent personas follow, and dynamic per-turn context is appended last to avoid cache invalidation.

The complete assembly sequence comprises:

1. **Safety (`safety`)** — Static core constraints loaded from `core/safety.txt` (`PromptFile.CORE_SAFETY`). Enforces absolute prohibitions against recursive system deletion, raw disk writes, firewall/SELinux disablement, data exfiltration, backdoor creation, credential display, and privilege escalation. Defines indirect credential verification, authorized data masking rules, and human escalation thresholds.
2. **Loyalty (`loyalty`)** — Static governance doctrine loaded from `core/loyalty.txt` (`PromptFile.CORE_LOYALTY`). Implements the mission-over-moment principle, treats user escalation and frustration as diagnostic data, requires active memory of prior denials, establishes visible dissent rules, and dictates authorized warning sequences (`warning → acknowledgement → execution`).
3. **Dissent (`dissent`)** — Static warning and disagreement protocol loaded from `core/dissent.txt` (`PromptFile.CORE_DISSENT`). Defines conditions for emitting warnings before tool execution, specifies historical denial evaluation, details posture-specific handling for triage states (`escalated`, `adversarial`, `confused`), and prescribes the format for substantive technical disagreement.
4. **Capabilities (`capabilities`)** — Mode-dependent operational scope loaded via `load_mode_prompts` based on `AgentMode` (e.g., `modes/operator_bound/capabilities.txt`, `modes/cloud_operator_bound/capabilities.txt`, or `modes/operator_not_bound/capabilities.txt` with a `_no_search.txt` fallback).
5. **Execution (`execution`)** — Mode-dependent execution workflow rules loaded via `load_mode_prompts` (e.g., `modes/operator_bound/execution.txt`, `modes/cloud_operator_bound/execution.txt`, or `modes/operator_not_bound/execution.txt`).
6. **Tools (`tools`)** — Mode-dependent tool guidelines and available tool listings loaded via `load_mode_prompts` (e.g., `modes/operator_bound/tools.txt`, `modes/cloud_operator_bound/tools.txt`, or `modes/operator_not_bound/tools.txt`). Injected when an Operator is bound or when web search is enabled. Mode tools files contain high-level rules only and never duplicate individual parameter specs.
7. **Response Constraints (`response_constraints`)** — Communication rules loaded from `system/response_constraints.txt` (`PromptFile.SYSTEM_RESPONSE_CONSTRAINTS`). Enforces concise, evidence-grounded reporting, guidelines for asking questions in the text response channel, UI output awareness, and omission of internal tool names and implementation details.
8. **Agent Persona (`agent_persona`)** — Persona-specific identity block generated by `AgentPersonaModel.get_system_prompt()`. Wraps `<role>`, `<output_contract>`, `<identity>`, `<purpose>`, and `<autonomy>` XML tags. If no agent name is specified, falls back to `core/identity.txt` (`PromptSection.IDENTITY`). Deep reasoning discipline (`<agentic_reasoning>`) resides exclusively in Sage's persona, leaving Dash unencumbered for low-latency responses.
9. **System Context (`system_context`)** — Dynamic XML block (`<system_context>`) populated from `OperatorContext` objects representing connected Operators. Injects host metadata including operating system, hostname, username, UID, shell, working directory, container runtime, init system, and cloud subtype with granted intents. Multi-operator environments wrap each host in `<operator index="...">` blocks.
10. **Sentinel Mode (`sentinel_mode`)** — Dynamic constraints loaded from `system/sentinel_mode.txt` (`PromptFile.SYSTEM_SENTINEL_MODE`) when `sentinel_mode` is enabled for the investigation. Informs the agent of data scrubbing placeholders (e.g., `[JWT]`, `[AWS_KEY]`, `[EMAIL]`), lists preserved operational data (IPs, hostnames, file paths, ARNs), and instructs indirect verification.
11. **Triage Context (`triage_context`)** — Dynamic XML block (`<triage_context>`) carrying the triage classification (`request_posture: normal | escalated | adversarial | confused` and `intent_summary`). Consumed directly by the dissent protocol to calibrate warning thresholds.
12. **Investigation Context (`investigation_context`)** — Dynamic XML block (`<investigation_context>`) summarizing case title, description, status, priority, severity, conversation history availability, and bound operator count.
13. **Learned Context (`learned_context`)** — Dynamic XML block (`<learned_context>`) containing long-term user communication preferences, technical background, and past investigation summaries retrieved by Codex from `InvestigationMemory`.

## Agent Modes

The execution mode determines which capabilities, execution rules, and toolsets are injected into the system prompt. Agent modes are defined in `app.constants.prompts.AgentMode` and sourced from `protocol/constants/prompts.json`:

- **`g8e.bound` (`AgentMode.G8E_BOUND`)** — Active when standard Operator instances are connected. Grants direct command execution, file system operations, and host inspection tools.
- **`g8e.cloud.bound` (`AgentMode.CLOUD_OPERATOR_BOUND`)** — Active when Cloud Operator instances (e.g., AWS) are connected. Enforces intent-based least-privilege access, cloud-specific execution semantics, and cloud tool routing.
- **`g8e.not.bound` (`AgentMode.G8E_NOT_BOUND`)** — Active when no Operator is bound. Limits agent operation to advisory, educational, and search-based troubleshooting without direct execution. Automatically switches to no-search templates (`capabilities_no_search.txt`, `execution_no_search.txt`) if web search is disabled.

## Tribunal Command Generation Prompts

The five-member Tribunal derives concrete shell commands from Sage's natural-language intent. Tribunal prompting operates under strict Information Isolation, where members generate commands independently without visibility into other members' identities or outputs.

Tribunal prompt composition follows a consumer-scaffolding pattern:

- **Consumer Template Ownership** — Persona models provide pure voice without string formatting placeholders. Scaffolding variables (`{request}`, `{guidelines}`, `{os}`, `{shell}`, `{user_context}`, `{operator_context}`, `{forbidden_patterns_message}`, `{command_constraints_message}`) are owned and populated by the consumer templates in `app/prompts_data/tribunal/`.
- **Round 1 Generation (`tribunal/generator.txt`)** — Injected with operator context, forbidden patterns, active command constraints (whitelists and blacklists), and Sage's intent. All five Tribunal members execute in parallel using their respective persona system prompts (`axiom`, `concord`, `variance`, `pragma`, `nemesis`) and emit single, unadorned shell command strings.
- **Round 2 Reflection (`tribunal/generator_round_2.txt` and `tribunal/round_2/<member>.txt`)** — When Round 1 voting fails to reach consensus, members evaluate anonymized candidate command clusters alongside persona-specific reflection guidance to resolve syntax disagreements or safety edge cases.
- **Auditor Evaluation (`tribunal/auditor.txt`)** — Injected with the consensus mode (`unanimous`, `majority`, or `tied`), winning command, and candidate cluster support counts via `build_tribunal_auditor_context`. The Auditor persona evaluates the commands and returns a structured JSON verdict with a status of `ok`, `revised`, or `swap`.

## Tool Descriptions and Alignment Contract

Tool descriptions are decoupled from system prompts and mode definitions to preserve prompt modularity and prevent drift:

- **Dedicated Tool Files** — Every active tool in `OperatorToolName` (`app.constants.generated_status`) has a 1:1 corresponding description file in `app/prompts_data/tools/<name>.txt` (e.g., `run_commands_with_operator.txt`, `file_read_on_operator.txt`, `grant_intent_permission.txt`).
- **Tool Description Structure** — Tool files define `<parameters>`, `<returns>`, and `<behavior>` blocks used by `AIToolService` tool classes to build tool declarations for LLM providers.
- **Mode File Rules-Only Invariant** — Mode tool files (`modes/*/tools.txt`) contain only high-level tool advertisements and usage rules. They are strictly prohibited from embedding parameter bullet lists or `<parameters>` tags.
- **Reasoning Discipline Placement** — Deep agentic reasoning guidelines (`<agentic_reasoning>`) reside exclusively on Sage's persona model (`SagePersona`), preventing leakage into mode files or fast-path personas (`DashPersona`).

## Prompt Loading and Caching

Prompt loading is handled by `app.prompts_data.loader`:

- **`load_prompt(prompt_file: PromptFile) -> str`** — Loads prompt files relative to the `prompts_data` directory. Cached with `@lru_cache(maxsize=128)` and raises `ResourceNotFoundError` if a file is missing.
- **`load_mode_prompts(operator_bound, is_cloud_operator, g8e_web_search_available) -> dict[str, str]`** — Resolves and loads the capability, execution, and tools files corresponding to the active `AgentMode`. Cached with `@lru_cache(maxsize=16)`.
- **`clear_cache()`** — Clears prompt caches for testing and hot-reloading.

## Protocol Alignment and Single Source of Truth

Prompt constants and identifiers are synchronized across the repository:

- **Protocol SSOT (`protocol/constants/prompts.json`)** — Defines canonical strings for `AgentMode` (`g8e.bound`, `g8e.not.bound`, `g8e.cloud.bound`) and `PromptSection` (`safety`, `loyalty`, `dissent`, `capabilities`, `execution`, `tools`, `response_constraints`, `agent_persona`, `identity`, `system_context`, `sentinel_mode`, `triage_context`, `investigation_context`, `learned_context`). See [Protocol Reference](../architecture/protocol.md) for the platform-level protocol constant registry.
- **Go Constants (`internal/constants/prompts.go`)** — Mirrors protocol values for backend and gateway routing.
- **Python Enums (`app.constants.prompts`)** — Re-exports protocol values via `g8e.constants.prompt()` for runtime typing, defining `AgentMode`, `PromptSection`, `PromptFile`, and `InvestigationContextLabel`.
- **Drift Prevention Tests** — Unit test suites (`test_prompt_alignment.py`, `test_prompts.py`, `test_prompt_loader.py`, `test_prompts.py` in `tests/unit/constants/`) enforce that all active tools have prompt files, no format placeholders leak into personas, and prompt sections match protocol definitions.
