## [1.7.7] - 2026-08-18

### Overview

Headless CLI enrollment: a new `--headless` flag on `g8e auth enroll` opts into a CLI-only identity that completes enrollment without a browser, and a new `g8e auth approve-recovery <token>` subcommand lets an already-enrolled CLI approve or deny a pending recovery request over mTLS. Together these enable fully automated CLI enrollment in CI, remote servers, and other environments without a browser or passkey authenticator. The resulting identity is mTLS-only and cannot authenticate to the Console SPA; a browser passkey can be registered later if console access is desired. All existing security properties of the recovery flow (one-time-use opaque token, TTL bounding, proof-of-possession on completion, active-user requirement, fail-closed mTLS classification) are preserved on the new approval path.

### Added

* **`--headless` flag on `g8e auth enroll`** — Opts into a CLI-only identity. Skips the passkey ceremony (no WebAuthn registration) and OS trust installation (the `--no-system-trust` behavior is implied; the CLI mTLS trust bundle is still installed from the recovery artifacts). On the recovery branch (partial/corrupt local identity on a bootstrapped gateway), prints `g8e auth approve-recovery <token>` for an already-enrolled CLI to run instead of opening a browser, then continues polling `recovery/status` and completing recovery exactly as the browser path does. On the bootstrap branch (unbootstrapped gateway), enrollment proceeds over plain HTTP with no approval needed and no passkey ceremony, producing a CLI-only identity. The resulting identity is mTLS-only: it can do everything the CLI could do before (MCP, A2A, governance, SSE, rotation) but cannot authenticate to the Console SPA. `Headless` implies `SkipPasskey` but also drives the recovery-branch output change; internal callers (`mcp agent run`, `demos`) set `SkipPasskey` directly and must NOT set `Headless`.
* **`g8e auth approve-recovery <token>` CLI subcommand** — The CLI-side counterpart to the browser Console SPA approve action. Uses the local enrolled CLI identity (mTLS) to approve or deny a pending recovery request created by another CLI's `auth enroll --headless` run. Posts to `POST /api/v1/auth/cli/recovery/approve-cli` (`RouteAuthMTLS`) with the token and `Approve: true` (default) or `Approve: false` (`--deny`), then prints the resulting approved/denied state. Wraps `ErrCLIRecoveryRequestFailed` for any other state. Follows the `approveCmdWithConfig` pattern with `configLoader`, `apiClientFactory`, and `fileSvcFactory` injection.
* **`POST /api/v1/auth/cli/recovery/approve-cli` endpoint** — The mTLS counterpart to the browser recovery-approve endpoint. Classified `RouteAuthMTLS`; the unified auth middleware (`handleMTLSAuth` → `handleCLIAuth`) verifies the CLI certificate URI SAN via `wid.MatchesCLI`, confirms the session is active, and stamps `ContextKeyUserID` / `ContextKeyCLISessionID` into the request context. The handler reads the approver user ID from the context (never from request body fields), verifies the user is active via `userSvc.GetByID` + `IsActive()`, and calls the same `recoverySvc.Approve(token, userID)` / `recoverySvc.Deny(token, userID)` transition as the browser path. The atomic state machine is unchanged. Registered in `gateway_auth.go` (`NewRouteAuthRegistry`) and `gateway_http_router.go` (`buildPublicRouter`). The new `AuthCLIRecoveryApproveCLI` constant is added to `internal/constants/api_paths.go` and synced to `protocol/constants/api_paths.json` and `protocol/python/g8e/_data/api_paths.json`.
* **`Headless` field on `auth.EnrollmentOptions`** — User-facing `--headless` flag opts into CLI-only identity, delegates recovery approval to an already-enrolled CLI via `g8e auth approve-recovery <token>` over mTLS. Distinct from the internal-only `SkipPasskey` field.

### Changed

* **`CLIRecoveryController` handles both browser and mTLS approval** — `handleRecoveryApproveCLI` is the mTLS counterpart to `handleRecoveryApprove`. The controller doc comment and auth classification documentation are updated to reflect the new `approve-cli = RouteAuthMTLS` classification alongside the existing `approve = RouteAuthWebSession`. The atomic recovery state machine (`recoverySvc.Approve`/`Deny`) is shared between both paths; no new states or transitions are introduced.
* **`EnrollmentCoordinator.handleRecovery` branches on `Headless`** — Under `--headless`, the coordinator prints `g8e auth approve-recovery <token>` for an already-enrolled CLI to run instead of opening a browser, then continues polling `recovery/status` and completing recovery exactly as the browser path does. The browser opener and passkey registrar are not called under `--headless`. `opts.SkipPasskey = opts.SkipPasskey || opts.Headless` ensures the passkey ceremony is suppressed.
* **Documentation reconciled with the headless enrollment code surface** — `docs/architecture/auth.md` adds a "Headless CLI Enrollment (mTLS-Only)" subsection documenting the `--headless` flag, the mTLS approve-cli endpoint, the `g8e auth approve-recovery` subcommand, and the unchanged security properties. `docs/architecture/network.md` adds the `approve-cli` endpoint to the CLI recovery and rotation routes section. `docs/architecture/gateway.md` updates the HTTPS router auth-mode classification to list the `approve-cli` endpoint under mTLS-only and clarify the browser approve under web-session-only. `docs/devs/codemap.md` updates the `CLIRecoveryController` description and the `approve_recovery.go` command entry. `docs/devs/troubleshooting.md` adds a `--headless` flag section and updates the CLI recovery section to document both approval paths. `docs/devs/tests.md` updates the `cli_recovery_controller_test.go` description to cover the mTLS approve-cli tests. `docs/reference/compliance-alignment.md` updates the human-approved CLI recovery flow bullet to mention both browser and mTLS approval paths. `protocol/docs/constants.md` adds `AuthCLIRecoveryApproveCLI` to the Auth API path list.

### Security

* **mTLS approve-cli endpoint is fail-closed** — `POST /api/v1/auth/cli/recovery/approve-cli` is classified `RouteAuthMTLS`. Unknown routes default to `RouteAuthMTLS`. No auth-bypass path is introduced. A request with no client certificate is rejected by the unified auth middleware with 401 (`ErrMTLSCertRequired`) before the handler runs.
* **Approver identity is derived from the verified mTLS certificate, never from the request body** — The unified auth middleware verifies the CLI certificate URI SAN via `wid.MatchesCLI`, confirms the session is active, and stamps `ContextKeyUserID` into the request context. The handler reads the approver user ID exclusively from the context. The request body carries only the token and approve/deny flag.
* **Revoked cert and inactive user are rejected** — A revoked CLI certificate is rejected by the middleware's `VerifyCertificate` (401, `ErrMTLSCertRevoked`) before the handler runs. A deactivated user is rejected by the handler's active-user check via `userSvc.GetByID` + `IsActive()` (403).
* **Recovery token remains one-time-use, opaque, and TTL-bounded** — The mTLS approve endpoint consumes the same `recoverySvc.Approve(token, userID)` transition as the browser path. Expired or replayed tokens are rejected on both approval paths.
* **Proof-of-possession on `recovery/complete` is unchanged** — The new CLI must still sign the request ID with its CSR private key. Stealing the token alone is not sufficient to complete recovery, regardless of which approval path was used.
