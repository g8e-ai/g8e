## [1.7.4] - 2026-08-15

### Overview

Demo, packaging, and enrollment refactor for v1.7.4. The release consolidates the Docker build into a single always-FIPS Dockerfile, rewrites the healthcare demo to use the native `run_shell_command` tool via a `paop` wrapper instead of a custom MCP downstream, removes notary/passkey enrollment and posture switching from the `demos run <org>` automated orchestration so DHS and FedRAMP demos are real end-to-end smoke tests that run with zero human interaction, makes passkey enrollment required only for notary posture (optional for doctrine and consensus) with a blocking browser-restart gate in `auth enroll` after the trust store changes, fixes the frontend demo's CORS and passkey-challenge status-code assertions, makes `gw start` copy the running binary into `.g8e/bin/` so the re-executed gateway process has a stable binary location that survives rebuilds or moves of the original executable, and fixes the PyPI publish verification job to poll the PyPI JSON API before installing so CDN propagation races do not cause spurious verification failures.

### Changed

* **Single always-FIPS Dockerfile** — `Dockerfile.fips` is removed; the repo-root `Dockerfile` now always builds with `GOFIPS140=v1.0.0` set in the builder stage so the Go Cryptographic Module v1.0.0 (CMVP Cert #5247) is linked in at build time and the binary enters FIPS 140-3 approved mode on startup without any runtime env var. Enforcement remains a runtime setting (off by default; operators set `GODEBUG=fips140=only` for strict enforcement). The Dockerfile hardcodes `GOOS=linux GOARCH=amd64` and documents the OE matrix (tested OE: Alpine 3.20 on x86-64; vendor-affirmed OEs: Debian 12, Ubuntu 22.04/24.04). The runtime image is pinned to Debian 12 (Bookworm) by digest. `g8e version --fips` runs as a build-stage self-check.
* **Demos build from the repo-root Dockerfile** — `demos/Dockerfile` is removed. Each demo's `compose.yml` `build` stanza now uses `context: ../..` to build from the repo-root `Dockerfile` (the same production image, always-FIPS, compiles from source in-container using vendored modules). No pre-built binary is required for Docker Compose builds. `demos/fedramp/compose.fips.yml` is removed. The `demos/bin/g8e` binary is still used for host-side demo orchestration when present, but is no longer copied into containers.
* **Healthcare demo uses native `run_shell_command` via `paop` wrapper** — The healthcare demo no longer runs a custom MCP downstream (`pa_api_server.py`, the `pa-submission-service`/`message-broker`/`reporting-db`/`rabbitmq` containers, and the `--mcp-downstream-url` flag are removed). Instead, the agent's governed `run_shell_command` tool drives a `paop.sh` shell wrapper bind-mounted into both the gateway and operator containers. The four healthcare harness scenarios (`healthcare-success`, `healthcare-phi-blocked`, `healthcare-gold-card`, `healthcare-sla-breach`) switch from the custom `submit_pa`/`query_pa_status` MCP tools to `run_shell_command` with `paop` arguments. The `healthcare-phi-blocked` scenario now asserts fail-closed (returns an error if the exfiltration is accepted instead of noting a warning). `demo_healthcare.go` scenario narration is updated to reflect the native-tool path. `demos/healthcare/README.md` is rewritten to match.
* **Notary scenarios removed from `demos run`** — DHS scenario 2 (`dhs-release`, Cross-Domain Release requires Notary authority) and FedRAMP scenario 3 (`fedramp-escalate`, Resource Destruction Requires Authorizing Official) are removed from the `demos run <org>` orchestration. DHS drops from 5 to 4 scenarios; FedRAMP drops from 5 to 4 scenarios. Remaining scenarios are renumbered to be sequential (DHS: 1=ingest, 2=disconnected-ops, 3=cue, 4=purge; FedRAMP: 1=provision, 2=deny, 3=revert, 4=evidence-block). The `scenarioCounts` map and `demosRunCmd` Long help text are updated.
* **Posture switching removed from demos** — `switchDemoPosture`, `switchDHSPosture`, and `switchFedRAMPPosture` are removed. The gateway boots in the posture defined by the compose file (consensus for DHS/FedRAMP) and is not restarted mid-demo. The FedRAMP L1-reject scenarios (`fedramp-deny`, `fedramp-evidence-block`) run under consensus posture; L1 doctrine rejection fires at admission before L2 consensus is consulted, so the scenarios are valid without a posture switch.
* **Host-CLI enrollment infrastructure removed from demos** — `enrollDemoHost`, `hostIdentity` struct, `waitForDemoGateway`, `notaryScenarioLabel`, the `demoHTTPPort`/`demoHTTPSPort` helpers and their maps, and the enrollment block in `runDemosRun` are removed. Demos no longer enroll a host CLI identity or register a WebAuthn passkey. The `hostID` parameter is removed from `runDemosWithTUI`/`runAllScenarios`/`runScenario`/`runScenarioWithResult`/`runDHSScenario`/`runFedRAMPScenario`.
* **`harnessConfig` simplified to fixed connection params** — The `Posture` field (documentation-only dead code, never read by `harnessRun`) and the `ExtraFlags` map (the mechanism for conditionally-present flags like `cli-cert`/`cli-key`/`cli-ca`/`approval-url`/`user-id`/`cli-session-id`) are removed. `defaultHarnessConfig` no longer seeds `cli-cert`/`cli-key`/`cli-ca` (the `/host-creds/` mount is removed). `defaultDHSHarnessConfig`/`defaultFedRAMPHarnessConfig` are simplified to no-arg constructors returning `defaultHarnessConfig("agent-coalition")`/`defaultHarnessConfig("agent-runtime")` with no extra flags. `harnessRun` is simplified to a fixed-args builder: exec/run prefix + fixed `--mtls-url`/`--public-url`/`--cert`/`--key`/`--ca` flags + scenario name. The `sort` import is removed.
* **`HOST_G8E_PKI` volume mount removed from compose files** — The `${HOST_G8E_PKI:-/dev/null}:/host-creds:ro` mount in `demos/dhs/compose.yml` (agent-coalition volumes) and `demos/fedramp/compose.yml` (agent-runtime volumes) is removed. The mount existed to expose host CLI credentials for notary scenario CLI-auth submissions, which are no longer part of the automated demos.
* **`gw start` copies the binary to `.g8e/bin/`** — `ProcessManager.StartOperator` now copies the currently running executable into `.g8e/bin/<name>` (with `PermFileExecutable` 0755) and re-execs from that path instead of from `os.Executable()` directly. This gives the gateway subprocess a stable binary location that survives rebuilds or moves of the original executable. The copy is skipped when the destination already matches the source (same size and modtime), so repeated `gw start` calls do not rewrite an identical binary. `operatorBinaryName()` returns `g8e` or `g8e.exe` based on `runtime.GOOS`. The old `getOperatorBinary()` helper is removed.
* **FIPS workflow triggers on `Dockerfile`** — `.github/workflows/build-and-test-fips.yml` now triggers on changes to the repo-root `Dockerfile` instead of the removed `Dockerfile.fips`.
* **Passkey enrollment required only for notary posture** — `auth enroll` no longer requires a passkey for doctrine or consensus postures. Only notary posture enforces L3 proof (a human-registered passkey); doctrine and consensus postures are L3-audited but not L3-enforced, so the passkey ceremony is optional there. The `gw start` next-steps output is now posture-aware: it prints "Passkey Enrollment: Required" with L3-enforced guidance for notary, and "Passkey Enrollment: Optional" with a note that the user can enroll a passkey if they plan to restart in notary mode for doctrine/consensus. The `printNextSteps` function now reads the `GovernancePosture` argument it previously ignored, and the `gateway.go` `Next step` line branches on `posture.RequiresL3Proof()`.
* **Blocking browser-restart gate in `auth enroll`** — After the trust store is modified (a new root CA is installed or stale anchors are removed, including under `--no-system-trust`), `EnrollmentCoordinator.Enroll` now blocks and prompts the user to close all open browser windows and press Enter before proceeding to the passkey ceremony. Previously the coordinator printed a non-blocking directive and continued immediately. The gate is skipped when `SkipPasskey` is set (internal callers like `mcp agent run` and demos inject an auto-continue `ContinueFunc` and open no browser themselves, so the prompt would pollute non-interactive output streams). The gate is also skipped when the trust store was unchanged this run (root already trusted, no stale anchors removed). The command-layer final summary no longer prints the stale "Close all open browser windows" guidance — the coordinator's gate handles it at the correct time (before the passkey ceremony).
* **Passkey enrollment URL printed to terminal before browser opens** — The `passkeyRegistrar` now prints the clickable enrollment URL via the coordinator's `OutputFunc` before opening the browser, so the URL is in the terminal scrollback regardless of TUI rendering behavior (no-TTY over SSH, TUI rendering failure, etc.). The insertion point is after the SSE ready-gate fires, so the user cannot click the URL before the SSE listener is connected. Browser-open-failure warnings are also routed through `OutputFunc` instead of `os.Stderr` directly, maintaining the coordinator's "no direct stdout/stderr writes" invariant. The URL is prefixed (`Passkey enrollment URL:`) so it is grep-able in scrollback and unambiguous in test assertions.

### Fixed

* **PyPI publish verification CDN race** — The `verify-install` job in `.github/workflows/release-python-protocol.yml` retried `pip install g8e==<version>` directly against pip's CDN-cached index. The package was successfully uploaded to PyPI but a CDN edge (macOS runner in the v1.7.3 release) never propagated the new version within the retry window, causing a spurious verification failure on a successful publish. The job now polls the PyPI JSON API (`https://pypi.org/pypi/g8e/json`) until the version appears in `releases`, then runs `pip install --no-cache-dir g8e==<version>` on ubuntu/macos/windows with import verification. Polling the API (rather than pip's CDN-cached index) avoids the "No matching distribution" failure when a CDN edge has not yet propagated.
* **FedRAMP `verify_ops.py` KSI path** — The `fedramp-cloudsvc` container now mounts `fedramp-gateway-state:/root/.g8e:ro` so `verify_ops.py` can read the KSI history from the gateway's compliance directory. `verify_ops.py` hardcodes the log and KSI result paths instead of reading them from env vars that were never set in the compose file.
* **Frontend demo CORS and passkey-challenge assertions** — The frontend demo's CORS preflight step now expects HTTP 204 (No Content) per the Fetch spec instead of 200; the gateway's `corsMiddleware` short-circuits OPTIONS with 204 and `Access-Control-Allow-*` headers. The passkey challenge endpoint step now accepts 200 or 400: 200 when no users exist yet (`createUserOnBootstrap` mints the first user) or 400 `ErrUserIDRequired` once the demo operator has created users — either proves the endpoint is reachable and enforcing input validation. A new `demoStepHTTPAny` helper validates against any of a set of expected status codes; `demoStepHTTP` delegates to it with a single-element slice.

### Out of Scope

* Notary posture itself is not removed from the platform. The gateway still supports notary posture, the harness still has notary scenarios, and `demos scenarios run <notary-scenario>` still works for manual testing against a manually-started demo with a manually-enrolled passkey. Only the `demos run <org>` automated orchestration excludes notary.
* The `demos scenarios run` command and the harness scenario registry are not changed. Notary scenarios remain available there. The `--cli-cert`/`--cli-key`/`--cli-ca` flags remain in `scenarios_run.go` for the manual notary testing path.
* The `--tui` flag for `demos run` stays. The TUI emitter code stays. It just no longer receives notary-related events.
* The `gw start --follow` (foreground) path is unchanged; it runs the gateway in-process and does not re-exec, so the binary copy does not apply there.
